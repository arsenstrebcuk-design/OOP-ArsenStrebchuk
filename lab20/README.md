# Лабораторна робота №20 — SRP: декомпозиція OrderProcessor

## Тема та мета

**Тема:** SRP (Single Responsibility Principle) — декомпозиція класу `OrderProcessor`.

**Мета:** застосувати принцип єдиної відповідальності для розбиття складного класу `OrderProcessor` на менші, сфокусовані компоненти.

## Що таке SRP і в чому була проблема

**Принцип єдиної відповідальності:** клас повинен мати лише одну причину для зміни, тобто відповідати за одну задачу.

Початковий клас `OrderProcessor` (файл `OrderProcessor.cs`) **порушує SRP** — у методі `ProcessOrder` він одночасно:

1. валідує замовлення;
2. зберігає його в "базу даних";
3. надсилає email клієнту;
4. оновлює статус.

Це чотири різні відповідальності в одному класі. Будь-яка зміна (інша БД, інший поштовий сервіс, нові правила валідації) змушує правити один і той самий клас — його важко тестувати, розширювати й повторно використовувати.

## Рефакторинг за SRP

Функціональність розбито на окремі інтерфейси та їхні реалізації:

| Інтерфейс | Відповідальність | Реалізація |
|-----------|------------------|------------|
| `IOrderValidator` | `bool IsValid(Order order)` — валідація | `OrderValidator` |
| `IOrderRepository` | `Save`, `GetById` — збереження/отримання | `InMemoryOrderRepository` |
| `IEmailService` | `SendOrderConfirmation` — надсилання листів | `ConsoleEmailService` |

**`OrderService`** — новий клас-координатор. Він не містить логіки валідації, збереження чи надсилання листів, а лише керує процесом, отримуючи всі залежності через конструктор (**Dependency Injection**). Тепер кожен клас має рівно одну причину для зміни, а реалізації легко підмінити без правок у `OrderService`.

### Файли

- `Order.cs` — сутність `Order` + `enum OrderStatus`.
- `OrderProcessor.cs` — початкова версія, що порушує SRP (для порівняння "до").
- `IOrderValidator.cs`, `IOrderRepository.cs`, `IEmailService.cs` — інтерфейси ("після").
- `OrderValidator.cs`, `InMemoryOrderRepository.cs`, `ConsoleEmailService.cs` — реалізації.
- `OrderService.cs` — координатор з Dependency Injection.
- `Program.cs` — демонстрація в `Main` для валідного та невалідного замовлень.

## Приклад запуску

```
=== Валідне замовлення ===
[Repository] Замовлення #1 збережено (у пам'яті).
[Email] Підтвердження надіслано Іван Петренко щодо замовлення #1.
[OrderService] Замовлення #1 оброблено. Статус = Processed.

=== Невалідне замовлення (сума <= 0) ===
[OrderService] Замовлення #2 відхилено: сума 0 некоректна. Статус = Cancelled.

=== Перевірка GetById через репозиторій ===
Знайдено замовлення #1 клієнта Іван Петренко, статус Processed.
Замовлення #2 не знайдено (не збережено, бо було невалідне).
```
