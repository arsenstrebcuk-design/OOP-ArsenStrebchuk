# Лабораторна робота №23 — ISP & DIP: рефакторинг і DI через конструктор

**Варіант 8: Employee Report System (PayrollSystem)**

## Тема та мета

**Тема:** ISP & DIP — рефакторинг і Dependency Injection через конструктор.

**Мета:** застосувати принципи розділення інтерфейсу (ISP) та інверсії залежностей (DIP) для рефакторингу коду, а також реалізувати DI через конструктор для зменшення зв'язаності та покращення тестування.

## Опис початкової структури

`PayrollSystem` рахує зарплату, генерує PDF-звіт і зберігає його в БД. У початковій версії клас:

- **сам створює** свої залежності всередині себе: `new SalaryCalculator()`, `new PdfExporter()`, `new SqlDatabase()`;
- залежить від конкретних «товстих» класів `PdfExporter` (з методами `ExportToExcel`, `Print`) та `SqlDatabase` (з методами `Load`, `Delete`, `Backup`).

## Аналіз порушень

### Порушення DIP (інверсія залежностей)

DIP вимагає, щоб високорівневі модулі залежали від абстракцій, а не від конкретних низькорівневих класів. Тут `PayrollSystem` (високий рівень) **напряму створює й тримає** конкретні `PdfExporter` і `SqlDatabase` (низький рівень). Наслідки:

- не можна підмінити реалізацію (напр. PDF → Excel, SQL → in-memory) без зміни `PayrollSystem`;
- клас неможливо протестувати ізольовано — він завжди тягне справжню БД та експортер;
- високий рівень жорстко прив'язаний до деталей нижнього рівня.

### Порушення ISP (розділення інтерфейсу)

ISP вимагає, щоб клієнт не залежав від методів, яких не використовує. `PayrollSystem` потребує лише «експортувати звіт» і «зберегти запис», але залежить від:

- `PdfExporter`, який несе ще `ExportToExcel` і `Print`;
- `SqlDatabase`, який несе ще `Load`, `Delete`, `Backup`.

Тобто клієнт прив'язаний до роздутих класів із купою методів, що йому не потрібні.

## Опис змін (рефакторинг)

### ISP — вузькі інтерфейси

Виділено вузькоспеціалізовані інтерфейси, кожен лише під конкретну потребу:

| Інтерфейс | Метод | Призначення |
|-----------|-------|-------------|
| `ISalaryCalculator` | `Calculate(...)` | розрахунок зарплати |
| `IReportExporter` | `Export(content)` | експорт звіту |
| `IReportRepository` | `Save(data)` | збереження запису |

Реалізації: `SalaryCalculator`, `PdfExporter`, `SqlReportRepository`. Тепер `PayrollSystem` бачить рівно ті методи, що використовує.

### DIP — впровадження залежностей через конструктор

`PayrollSystem` більше нічого не створює всередині. Усі залежності описані як інтерфейси й **передаються в конструктор**:

```csharp
public PayrollSystem(ISalaryCalculator calculator, IReportExporter exporter, IReportRepository repository)
```

Тепер клас залежить лише від абстракцій. Реалізації збираються ззовні (у `Main`) і легко підміняються — наприклад, на `ConsoleReportExporter` та `InMemoryReportRepository` без жодної зміни `PayrollSystem`.

## Висновки

Початкова версія `PayrollSystem` була жорстко зв'язана з конкретними класами й залежала від їхніх зайвих методів. Після рефакторингу:

- **ISP** — вузькі інтерфейси прибрали залежність від непотрібних методів;
- **DIP** — інверсія залежностей зробила високорівневий клас незалежним від деталей;
- **DI через конструктор** — дозволив збирати систему ззовні й підміняти реалізації (реальна БД / мок для тестів) без зміни `PayrollSystem`.

Разом це знижує зв'язаність, спрощує розширення й робить код тестованим.
