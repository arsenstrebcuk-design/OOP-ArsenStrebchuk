# Лабораторна робота №22 — LSP: виявлення порушень і альтернативи

**Варіант 8: List & ReadOnlyList**

## Тема та мета

**Тема:** LSP (Liskov Substitution Principle) — виявлення порушень і альтернативи.

**Мета:** поглибити розуміння принципу підстановки Лісков, навчитися ідентифікувати його порушення в ієрархіях класів та застосовувати альтернативні підходи (композиція, зміна ієрархії) для створення LSP-сумісних рішень.

## Опис початкової ієрархії

- **`CustomList`** (базовий) — список із методом `Add(item)`. Контракт `Add`: після виклику список містить `item`, а `Count` зростає на 1.
- **`ReadOnlyList : CustomList`** (похідний) — список лише для читання. Перевизначає `Add`, але замість додавання кидає `NotSupportedException`.

Клієнтський метод `FillList(CustomList list, int count)` написаний під базовий тип і очікує, що `Add` завжди працює.

## Аналіз порушення LSP

**LSP:** об'єкти похідного класу мають бути взаємозамінними з об'єктами базового класу без порушення коректності програми.

`ReadOnlyList` цей принцип **порушує**:

- Базовий клас `CustomList` обіцяє контракт: `Add(item)` додає елемент.
- Похідний `ReadOnlyList` цей контракт **не виконує** — він кидає виняток замість додавання.
- Отже `ReadOnlyList` **не є** справжнім підтипом `CustomList`. Будь-який код, написаний під `CustomList` і розрахований на робочий `Add()` (як `FillList`), зламається, щойно йому передати `ReadOnlyList`.

Порушується саме **поведінковий контракт (постумова)** методу `Add` базового класу: похідний клас звужує допустиму поведінку до неможливості виконати операцію. Це класичний «відмовний» антипатерн (refused bequest) — спадкоємець відмовляється від частини успадкованого інтерфейсу.

## Обраний підхід: зміна ієрархії + композиція

Замість того щоб пхати незмінюваний список у ту саму ієрархію, що й змінюваний, **розділяємо контракти**:

- **`IReadableList`** — лише читання (`Count`, індексатор, перебір).
- **`IMutableList : IReadableList`** — додає `Add(item)`.
- **`MutableList : IMutableList`** — повноцінний змінюваний список, чесно виконує `Add`.
- **`ReadOnlyListView : IReadableList`** — список лише для читання через **композицію**: обгортає джерело `IReadableList`. Методу `Add` тут **немає взагалі**.

Клієнтські методи тепер вимагають рівно те, що їм треба:
- `FillMutable(IMutableList list, ...)` — потребує змінюваності;
- `Print(IReadableList list)` — потребує лише читання, працює з обома типами.

**Чому це дотримується LSP:** кожен клас повністю виконує контракт свого інтерфейсу. `ReadOnlyListView` не обіцяє `Add`, тож і зламати нічого не може. Передати read-only список у `FillMutable` неможливо — це помилка компіляції, а не сюрприз у рантаймі. Порушення усунене на рівні типів.

## Фрагменти коду

**Порушення (початкова версія):**
```csharp
public class ReadOnlyList : CustomList
{
    public override void Add(int item)
        => throw new NotSupportedException("ReadOnlyList не підтримує додавання елементів.");
}
```

**Виправлення (рефакторинг):**
```csharp
public interface IReadableList { int Count { get; } int this[int index] { get; } IEnumerable<int> Items { get; } }
public interface IMutableList : IReadableList { void Add(int item); }

public class ReadOnlyListView : IReadableList   // лише читання, БЕЗ Add
{
    private readonly IReadableList _source;
    public ReadOnlyListView(IReadableList source) => _source = source;
    // ... лише читабельні члени
}
```

## Висновки

LSP важливий тому, що дозволяє писати клієнтський код під базовий тип і бути впевненим, що він коректно працюватиме з будь-яким підтипом. Порушення LSP (як `ReadOnlyList`, що ламає успадкований `Add`) перетворює наслідування на джерело прихованих рантайм-помилок.

Перевага обраного підходу (розділення інтерфейсів + композиція): контракт стає чесним, а некоректні комбінації відсікаються ще на етапі компіляції, а не проявляються винятками під час виконання. Композиція тут природніша за наслідування — незмінюваний список не «є різновидом» змінюваного, тож і не повинен успадковувати його інтерфейс.
